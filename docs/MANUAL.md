# Offline manual | File Studio

Development source only. Launch the GUI after compiling. The Catalogue page creates or opens a SQLite catalogue, searches path fragments, shows scan history, and appends refreshed scans. To create a catalogue, choose the source folder and select **Create catalogue…**; choose a new `.sqlite` or `.sqlite3` path. Scanning runs in the background, reports indeterminate progress, can be cancelled, and refuses to overwrite an existing catalogue. After creation, the workspace opens the catalogue and loads its first scan snapshot. Search uses the catalogue snapshot and does not access the original volume. Search results use a sortable native table with 50 rows per page. Select a row and click **Inspect selected file**; choose the source folder first if you want to read the file contents. File Studio revalidates the relative path, refuses symbolic links, and displays read-only hashes, timestamps, a bounded hexadecimal sample and supported format properties. Search alone never opens the source file. Select the source folder and choose **Find duplicate candidates** to compare equal-size files by BLAKE3; the workspace shows groups with matching content hashes, paginates them, and does not move or delete anything. Hashing stops at a 1 GiB candidate-data budget. During a refresh, progress is indeterminate while File Studio discovers the directory contents, then shows a percentage while it writes the scan snapshot. **Cancel current job** stays available throughout and requests cooperative cancellation. The Operations page keeps the existing processing routes; choose an operation, enter an input path and a new output path where needed, set its parameter, then Run. Native file and folder dialogs are available on both pages. Choose a theme to change workbench colors. UI scale adjusts the controls from 80% to 300% and remembers appearance choices. Full screen-reader and accessibility verification remains open.

The Catalogue page provides the native create/open/search/history/refresh workflow. For automation, use the Operations page `scan` route and choose a new `.sqlite` file with **Save as…**. Use **Search** to browse saved paths, **Load history** to reread scan records, or choose the source folder and select **Add scan snapshot** to refresh. The sortable history table shows 20 scans per page; selecting one row fills the earlier scan ID, and selecting a second fills the later ID. The **Compare saved snapshots** panel accepts two scan IDs from the history table and displays added, removed, size-changed and same-size paths using only the SQLite catalogue; the report states whether the snapshots share a stable source identity. Refresh performs a complete read-only traversal and appends a new versioned snapshot; it does not replace earlier history. Keep the catalogue outside the scanned folder. A search is useful when the storage is disconnected, but results may be stale until you refresh.

- `duplicates`: Groups files with matching BLAKE3 content hashes after first grouping by size, with a 1 GiB candidate read budget. The native Catalogue workspace shows these groups for review; it does not delete or move files.
- `directory-usage`: Reports logical file sizes by top-level directory. Symlinks are skipped and hard links are counted by name. In the Catalogue workspace, **Analyze directory usage** presents the 20 largest top-level groups as a bounded native bar chart; it reads the selected folder and does not change files.
- `inspect`: A combined read-only report with the recognized signature subset, byte size, SHA-256/SHA-512/BLAKE3, available timestamps, a 64-byte hexadecimal/ASCII sample and verified PNG chunk counts. PNG metadata values are not decoded. Other format-specific properties are currently unavailable. Optional JSON output.
- `verify` checks the input against a SHA-256, SHA-512, or BLAKE3 checksum. Enter `sha256=HEX` or `blake3=HEX` in the operation parameter, using 64 hexadecimal digits, or `sha512=HEX` using 128 digits. Obtain the checksum from a trusted source. Leave the output blank for a preview or give it a new `.json` path for a report. A mismatch reports an error and creates no output.
- `age-keygen` creates a new age X25519 identity file at the chosen output path and displays its public recipient key. The saved file is private key material and has no passphrase protection. On Unix it is written with owner-only permissions. On Windows, identity files must be saved under your user profile and inherit that directory's access controls. Keep a secure backup and do not share the identity file.
- `age-encrypt` encrypts a regular file to the age X25519 public recipient key in Parameter and writes a new `.age` file. `age-decrypt` reads a regular age file and writes decrypted bytes to a new output path; enter the identity file path in Parameter. Both routes stream up to 4 GiB. On Windows, decrypted output must be saved under your user profile. Decryption publishes output only after the age stream authenticates successfully. Wrong keys, tampering, and collisions create no output.
- `zip-list`: List ZIP entries and declared sizes. Optional new JSON output. Member data is never expanded.
- `tar-list`: List safe TAR paths and declared member sizes. Optional new JSON output; member payloads are not read.
- `tar-test`: Validate TAR headers and fully read regular file members within the documented limits. TAR has no standard payload checksums.
- `tar-create-directory`: Create a new `.tar` from regular files in a directory tree.
- `tar-extract-entry`: Extract one regular entry by its one-based `tar-list` index to a new file.
- `tar-extract-all`: Safely extract regular files and directories to a new folder.
- `scan`: Bounded directory inventory; choose a new JSON, CSV or `.sqlite` output. A SQLite catalogue stores a local version 1 snapshot.

To verify the bundled sample from the command line:

```sh
cargo run --locked --no-default-features -- --cli verify tests/fixtures/abc.txt "" sha256=ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad
```

Limitations: Signature identification is a limited prefix test, not exhaustive or format validation. The integrated inspector provides format-specific properties only for bounded PNG chunk structure; timestamps can be unavailable, and its hex sample contains original bytes that may be sensitive. Age encryption does not prove who sent a file, and the generated identity is not passphrase-protected. The app does not yet create or verify digital signatures. Scanning aborts on unreadable entries; scans always traverse the full directory and do not use filesystem change journals. Unix scan-root identity uses device and inode; Windows uses the volume serial and root file index. Other targets or filesystems that do not provide an ID store each refresh as a full-rescan baseline without cross-snapshot deltas. Broad metadata sanitation and backup are not available. Archive creation omits empty directories and filesystem metadata. A locally stored checksum manifest can be edited by anyone who can modify it.

No output overwrite is allowed. No accounts, ads, telemetry or runtime downloads are intended. Do not use this unverified snapshot with valuable or hostile input. Citation and donations are voluntary.

Use `zip-test` to verify stored and Deflate entry data without extraction. It accepts archives up to 32 MiB and 4,096 entries, with a 32 MiB expansion limit per entry and 128 MiB per archive. Successful checks confirm decode and internal checksums. Extraction safety and authenticity require separate checks.

Use `gzip-create` with one regular file and a new `.gz` output to create a GZIP stream. Source and compressed output are limited to 1 GiB. The source is left unchanged. `gzip-test` validates the stream and CRC by decompressing into a sink without writing the content. `gzip-extract` decompresses a GZIP file, including concatenated members, to a new selected output file. Compressed input and expanded data are each limited to 1 GiB; output collisions, corrupt checksums and truncated streams are rejected. Operations stream in 32 KiB chunks and support cooperative cancellation. GZIP does not authenticate the publisher, scan for malware, or preserve source filesystem metadata. This route handles a single-file stream, not TAR or TAR.GZ directory archives.

The TAR routes support uncompressed POSIX/GNU TAR only; they do not handle `.tar.gz` or other compressed TAR variants. Archive input is limited to 160 MiB, 4,096 entries, 1,024 bytes per path, 32 MiB per regular file and 128 MiB expanded total. `tar-list` validates member types and paths but skips payload reads. `tar-test` checks TAR headers and reads each regular member fully to detect truncated entries. TAR has header checksums but no standard checksum for payload bytes, so this test cannot detect all payload corruption or establish authenticity. `tar-create-directory` creates a no-overwrite `.tar` from regular files, omits symlinks, empty directories and filesystem metadata, and checks source size/modification time while streaming. `tar-extract-entry` and `tar-extract-all` reject traversal, duplicate paths, links, special entries, size-limit violations and existing outputs. Full extraction reserves a new destination directory and removes that directory if extraction fails. Always review extracted content before opening it.

Use `hex-preview` with an optional `offset,length` parameter. The default is 256 bytes from offset zero. The maximum is 1,024 bytes. Prefix the offset with `0x` to enter hexadecimal. The report shows printable ASCII beside the hex values and may contain sensitive bytes.

Use `zip-create` with one regular file up to 16 MiB and a new `.zip` path. Leave the parameter blank to use the input filename, or enter a portable ASCII filename for the entry. This route preserves file bytes and uses a single flat entry. Ownership, original timestamps and extended attributes are omitted.

Use `zip-create-directory` with a directory and a new `.zip` path to archive up to 4,096 regular files, 32 MiB each and 128 MiB total. Symbolic links and empty directories are skipped. The operation checks source sizes and modification times while reading. Use `zip-extract-all` with a ZIP and a new destination folder. It rejects traversal, duplicate paths, links, encrypted or special files, and expansion beyond the same limits. It reserves the destination directory exclusively and creates each output file without overwriting. If extraction fails, the partial destination created by that attempt is removed. Review extracted content before opening it.

Use `manifest-create` with a directory and a new JSON output outside that directory. It records a schema version, SHA-256 algorithm, relative Unicode paths, byte sizes and hashes for up to 10,000 files and 1 GiB. `manifest-verify` takes the saved manifest as Input and its root directory as Parameter. It reports matching, changed and missing files; it rejects absolute/traversal paths, duplicate paths and symlinked path components. A checksum manifest does not prove who authored it.

To extract one file, first use `zip-list` and read its one-based entry number. Pass that number to `zip-extract-entry` and choose a new output file. Unsafe entry paths, symlinks, nonregular entries, CRC errors, files over 32 MiB expanded and output collisions are rejected.

Use `png-metadata` to count chunk types and identify removable metadata without reading tag values. Use `png-strip-metadata` with a new `.png` output to omit `tEXt`, `zTXt`, `iTXt`, and `eXIf` chunks. The report shows counts before and after. Image data and chunks such as ICC profiles remain. Treat the output as a selective metadata cleanup and review its contents before sharing.

Use `jpeg-metadata` to identify standard EXIF APP1, Adobe XMP APP1, and Photoshop APP13 (which may contain IPTC) segments in a JPEG header; it reports segment counts and does not decode tag values. `jpeg-strip-metadata` writes a new `.jpg` or `.jpeg` file, omitting those recognized segments before the first image scan while preserving other header segments, ICC APP2 profiles, scan headers, and compressed image bytes. Input is limited to 32 MiB. The route does not inspect metadata after the first scan or every proprietary variant, and it does not decode/re-encode pixels. Review output metadata before sharing; this is selective cleanup, not complete sanitation, redaction, or anonymity.

Use `exif-metadata` to read bounded tag values with the pure-Rust `kamadak-exif` parser for its supported JPEG, TIFF, HEIF/HEIC/AVIF, PNG, and WebP containers. This reports at most 512 fields and 1,024 UTF-8 bytes per displayed value from files up to 32 MiB. GPS coordinates, camera identifiers, and timestamps can be sensitive. EXIF inspection does not decode all XMP/IPTC fields and is not metadata removal; the JPEG cleanup route remains selective.

To create a persistent catalogue, use `scan` with a new `.sqlite` output outside the scanned directory tree. Schema version 3 stores scan timestamps, a root label, relative paths, file sizes, available modification times, and an opaque source identity. Unix uses filesystem device number and root-directory inode; Windows uses the `file-id` crate to pair volume serial and root-directory file index. These identities do not depend on the mount path. Other targets or filesystems without a readable stable ID use unknown identity and full-rescan baselines. If identity is unavailable or does not match, refresh does not infer changes across sources. Refresh always traverses the complete directory; it does not use filesystem change journals. When source identity matches, history reports additions and removals and classifies a path as changed when its size or available modification time changes. This metadata check can miss content changes that preserve both attributes. Schema-v1/v2 catalogues migrate on refresh without dropping snapshots; old rows have no modification time, so their first comparison uses size only. `catalog-history` lists the latest 100 scans. `catalog-search` accepts JSON or SQLite inventories and searches saved paths without opening the original volume. Catalogues include filenames and are private local data; treat them as sensitive. Database inputs are size-bounded and read-only during search.

## Additional operations

- `catalog-compare`. Open an earlier JSON or SQLite catalogue and enter a later inventory path of either format. The report lists added, removed, and size-changed paths. A same-size match can still have different contents.
- `catalog-refresh`. Input a directory and enter an existing `.sqlite` catalogue path as Parameter. Adds a complete scan snapshot; prior records remain intact. It reports changes only when the stored source identity matches, and otherwise marks the scan as a full-rescan baseline.
- `catalog-history`. Input a `.sqlite` catalogue to inspect its latest 100 snapshots without accessing the scanned paths.
- `catalog-compare-snapshots`. Input a `.sqlite` catalogue and pass JSON such as `{"before_scan_id":1,"after_scan_id":2}` to compare any two retained snapshots. This reads saved relative paths and sizes only; equal sizes do not prove equal contents, and the report exposes whether stable source identities match.
- `file-times`. Open a regular file. Times are reported in Unix epoch milliseconds. Unavailable timestamps appear as null.
